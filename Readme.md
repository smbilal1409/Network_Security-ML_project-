# PhishGuard AI — Network Security ML Pipeline

PhishGuard AI is an end-to-end **Machine Learning–based Network Security system** designed to analyze network/URL security data and predict whether an activity is **safe or potentially malicious**.

The project was built as a complete ML pipeline rather than simply training a model in a notebook. It covers the complete workflow from **data storage and ingestion to validation, transformation, model training, evaluation, artifact generation, and finally inference through a FastAPI web application**.

---

## Project Overview

The main objective of this project is to build a production-style machine learning pipeline capable of taking network security data, processing it through a sequence of automated stages, and generating predictions using a trained machine learning model.

The overall workflow is:


# 2. Data Storage — MongoDB Atlas

Instead of keeping the dataset only as a local CSV file, the project first stores the data in **MongoDB Atlas**.

This introduces a database layer into the ML workflow.

The architecture therefore begins with:

```text
Dataset
   ↓
MongoDB Atlas
   ↓
ML Pipeline
```

The application connects to MongoDB using the MongoDB connection string stored through an environment variable:

```text
MONGODB_URL_KEY
```

The database and collection are accessed through the project's configured:

```text
DATA_INGESTION_DATABASE_NAME
DATA_INGESTION_COLLECTION_NAME
```

This makes the data ingestion stage independent from the original local dataset.

---

# 3. Data Ingestion

The first major stage of the ML pipeline is **Data Ingestion**.

The responsibility of data ingestion is to retrieve the dataset from the configured data source and prepare it for the remaining pipeline stages.

In this project, the data source is MongoDB Atlas.

The ingestion process can be represented as:

```text
MongoDB Atlas
      │
      ▼
Read Dataset
      │
      ▼
Convert to DataFrame
      │
      ▼
Train / Test Split
      │
      ▼
Training Dataset
Testing Dataset
```

The ingestion component generates a `DataIngestionArtifact`.

The artifact contains paths to the generated training and testing datasets.

For example:

```text
DataIngestionArtifact

├── trained_file_path
└── test_file_path
```

This is important because the next pipeline stage does not need to know how the data was obtained.

It simply receives the artifact generated by Data Ingestion.

---

# 4. Data Validation

After ingestion, the data is passed to the **Data Validation** stage.

The purpose of data validation is to make sure that the data received by the pipeline has the expected structure before it is used for transformation and model training.

The validation stage checks the dataset against the project's predefined schema.

The schema defines the expected columns and their characteristics.

The process is:

```text
Training Data
      │
      ▼
Read Schema
      │
      ▼
Check Dataset Structure
      │
      ├── Valid
      │
      └── Invalid
```

The validation stage includes checking the expected number of columns.

The project also uses the **Kolmogorov–Smirnov (KS) test** to compare distributions between the relevant datasets.

The validation stage generates a:

```text
DataValidationArtifact
```

which provides the validated training and testing file paths for the next stage.

This creates a clean separation between:

```text
Raw/Ingested Data
```

and

```text
Validated Data
```

---

# 5. Data Transformation

Once the data has passed validation, it enters the **Data Transformation** stage.

This stage prepares the dataset so that it can be consumed by the machine learning model.

One of the important problems handled here is **missing values**.

The project uses:

```text
KNNImputer
```

from Scikit-learn.

The configured parameters are:

```python
{
    "missing_values": np.nan,
    "n_neighbors": 3,
    "weights": "uniform"
}
```

Therefore, when a missing value is encountered, the imputer looks at the **3 nearest observations** and uses uniform weighting to estimate the missing value.

---

## Transformation Pipeline

The transformation pipeline is implemented using Scikit-learn's:

```text
Pipeline
```

with:

```text
KNNImputer
```

as the processing step.

Conceptually:

```text
Input Features
      │
      ▼
KNN Imputer
      │
      ▼
Transformed Features
```

The target column:

```text
Result
```

is separated from the input features before transformation.

Therefore:

```text
Dataset
   │
   ├──────────────► Features
   │
   └──────────────► Target
```

The preprocessing object is **fitted only on the training features**:

```python
preprocessor.fit(input_feature_train_df)
```

The trained preprocessor is then used for both datasets:

```python
transform(training_data)
transform(testing_data)
```

This is an important part of a proper ML pipeline because the preprocessing logic learned from the training data is reused when processing unseen test data.

---

# 6. Saving the Transformation Object

The fitted preprocessing pipeline is saved as:

```text
preprocessor.pkl
```

This is extremely important for inference.

The web application does not create a new preprocessing pipeline when a user uploads a CSV.

Instead, it loads the already trained:

```text
preprocessor.pkl
```

and applies exactly the same preprocessing procedure that was used during model training.

The architecture becomes:

```text
Training
   │
   ├── Train preprocessing
   │
   └── Save preprocessor.pkl
                  │
                  ▼
              Inference
                  │
                  ▼
          Load preprocessor.pkl
```

This keeps the training and prediction pipelines consistent.

---

# 7. NumPy Transformation Artifacts

After transformation, the processed datasets are converted into NumPy arrays.

The transformed data is stored as:

```text
train.npy
test.npy
```

The transformed training data contains:

```text
Transformed Features + Target
```

and the transformed testing data contains:

```text
Transformed Features + Target
```

The generated artifacts therefore provide the model training stage with numerical data in a convenient format.

---

# 8. Model Training

After data transformation, the transformed training dataset is passed to the **Model Training** stage.

The purpose of this stage is to train a machine learning model using the processed training data.

The model learns the relationship between:

```text
Network Security Features
            ↓
        Target Result
```

The trained model is then serialized and saved as:

```text
model.pkl
```

Therefore, after model training, the project has two important inference artifacts:

```text
final_model/
│
├── model.pkl
└── preprocessor.pkl
```

These two files together represent the trained prediction system.

---

# 9. Model Evaluation

Training a model is not enough.

The trained model must also be evaluated to determine whether it performs sufficiently well on unseen data.

The project therefore includes a **Model Evaluation** stage.

The trained model is evaluated using the test data produced earlier in the pipeline.

Conceptually:

```text
Test Dataset
     │
     ▼
Trained Model
     │
     ▼
Predictions
     │
     ▼
Evaluation Metrics
```

The evaluation stage provides a way to compare model performance and determine whether the trained model is suitable for the final prediction stage.

This makes the project more than simply:

```text
train model → save model
```

Instead, it follows a structured:

```text
train → evaluate → accept/use model
```

workflow.

# 13. CSV-Based Prediction

The main prediction endpoint is:

```text
POST /predict
```

The user uploads a CSV file through the web interface.

The backend then:

1. Reads the uploaded CSV.
2. Loads `preprocessor.pkl`.
3. Loads `model.pkl`.
4. Creates the `NetworkModel`.
5. Passes the uploaded data through the prediction pipeline.
6. Generates predictions.
7. Adds the predictions to the uploaded DataFrame.
8. Saves the prediction output.
9. Displays the results through an HTML interface.

The complete inference flow is:

```text
User
 │
 ▼
Upload CSV
 │
 ▼
FastAPI
 │
 ▼
Read CSV
 │
 ▼
Load preprocessor.pkl
 │
 ▼
Load model.pkl
 │
 ▼
NetworkModel
 │
 ▼
Generate Predictions
 │
 ▼
Add predicted_column
 │
 ▼
Display Results
```

The project also includes dedicated logging and exception-handling components.

The pipeline records important events such as:

```text

Data transformation started
```




# PhishGuard AI

**PhishGuard AI** demonstrates how a machine learning model can be transformed from a training experiment into a structured, reusable, and interactive network security application.

The project focuses on the complete lifecycle of an ML system:

```text
Store → Ingest → Validate → Transform → Train → Evaluate → Predict → Visualize
```

with the final goal of making network-security predictions accessible through an interactive web interface rather than requiring users to interact directly with Python code or Jupyter notebooks.
